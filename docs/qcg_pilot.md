# QCG Pilot-Job on Remote Machines

QCG Pilot Job is a lightweight implementation of the Pilot Job mechanism which
can be used to run a very large number of jobs efficiently on remote clusters and supercomputers.

More information on QCG-PilotJob can be found on their [ReadTheDocs site](https://qcg-pilotjob.readthedocs.io/en/develop/).

## Quick Start

### 1. Setup FabSim3

```bash
git clone https://github.com/djgroen/FabSim3.git
cd FabSim3
python3 configure_fabsim.py
```

**Recommended**: python3 is your System Python (typically `/usr/bin/python3`)

### 2. Create Virtual Environment

```bash
fabsim <machine> create_virtual_env
```

### 3. Install QCG-PilotJob

```bash
fabsim <machine> direct_install_app:QCG-PilotJob,venv=true
```

### 4. Update Configuration

Add the virtual environment path to your `machines_user.yml`:

```yaml
<machine>:
  virtual_env_path: "/path/to/your/virtual/environment"
```

(e.g., virtual_env_path: "/work/d202/d202/mzr234/VirtualEnv")

### 5. Test Installation

```bash
fabsim localhost install_plugin:FabDummy
fabsim localhost dummy_ensemble:dummy_test,pj_type=qcg,venv=true
```

## Resource Configuration

Configure your machine resources in `machines_user.yml`:

```yaml
<machine>:
  cores: 256            # Total cores to request
  corespernode: 128     # Cores per node (hardware specific)
  cpuspertask: 2        # Cores per individual task
  taskspernode: 64      # Calculated: 128 ÷ 2 = 64
```

Fabric computes the node count from these values:

```
nodes = ceil(cores / corespernode)
```

and the SLURM header requests `--nodes=$nodes --ntasks-per-node=$taskspernode
--cpus-per-task=$cpuspertask`.

!!! warning "`cpuspertask` divides your concurrency"
    Each task asks QCG-PilotJob for `numCores = cpuspertask`, while the pool of
    schedulable slots is `nodes × taskspernode`. The number of **concurrently
    running** tasks is therefore

    ```
    concurrent_tasks = nodes × taskspernode ÷ cpuspertask
    ```

    With the block above (`cores=256`, `taskspernode=64`, `cpuspertask=2`) you get
    **2 nodes and 64 concurrent tasks** (32 per node) — *not* 128. If your
    application is single-threaded, set `cpuspertask=1` and cap the per-node load
    with `taskspernode` instead (see [Multi-node execution and resource
    tuning](#multi-node-execution-and-resource-tuning)).

## Usage Examples

### Basic Ensemble

```bash
fabsim <machine> <app>_ensemble:<config>,pj_type=qcg,venv=true
```

### With Replicas

```bash
fabsim <machine> <app>_ensemble:<config>,replicas=5,pj_type=qcg,venv=true
```

### Large Scale Example

```bash
fabsim archer2 dummy_ensemble:dummy_test,replicas=128,cores=256,pj_type=qcg,venv=true
```

### Custom Resource Allocation

```bash
fabsim <machine> <app>_ensemble:<config>,cores=512,cpuspertask=4,job_wall_time=2:00:00,pj_type=qcg,venv=true
```

## Key Parameters

| Parameter | Description | Example |
|-----------|-------------|---------|
| `pj_type=qcg` | Enable QCG-PilotJob | Required |
| `venv=true` | Use virtual environment | Recommended |
| `cores=N` | Total cores to allocate | `cores=512` |
| `cpuspertask=N` | Cores per task | `cpuspertask=4` |
| `replicas=N` | Run each task N times | `replicas=1` |
| `job_wall_time=H:M:S` | Maximum job duration | `job_wall_time=2:00:00` |

The number of nodes will be calculated by FabSim3.

## Refine with Upsampling

Upsampling allows you to selectively increase the number of replicas for specific ensemble runs that show high variability. Instead of using resources excessively on uniformly replicating all runs, you focus only on cases where uncertainty is high.

### Complete Upsampling Workflow

### Step 1: Initial Broad Sweep

Run all parameter combinations with just one replica:

```bash
fabsim <machine> <app>_ensemble:<config>,replicas=1,pj_type=qcg,venv=true
```

This might generate 1000 runs like run_0001, run_0002, ..., run_1000, if there are 1000 subdirectories in the SWEEP directory.

### Step 2: Analyze Variability

After the first ensemble run, analyze your results manually or via a script to identify high-variance cases.

Example analysis results:

- run_0089: Parameter variance = 0.85 (HIGH), generated by d0089 in SWEEP directory
- run_0234: Parameter variance = 0.92 (HIGH), generated by d0234 in SWEEP directory
- run_0567: Parameter variance = 0.78 (HIGH), generated by d0567 in SWEEP directory

### Step 3: Targeted Upsampling

Add more replicas only to these high-variance cases:

```bash
fabsim <machine> <app>_ensemble:<config>,upsample="d0089;d0234;d0567",replicas=10,pj_type=qcg,venv=true
```

Each of the three runs above will be repeated 10 more times.

Comparison:

- Without upsampling: 10 x all = 10,000 jobs
- With upsampling: 1000 + (3 x 10) = 1,030 jobs

### Step 4: Flexible Replicas Per Run

Add various replicas ONLY to the high-variance cases:

```bash
fabsim <machine> <app>_ensemble:<config>,upsample="d0089;d0234;d0567",replicas="5;2;3",pj_type=qcg,venv=true
```

- d0089 → 5 replicas
- d0234 → 2 replicas
- d0567 → 3 replicas

### Step 5: Prioritizing with `exec_first`

```bash
fabsim <machine> <app>_ensemble:<config>,upsample="d0089;d0234;d0567",replicas="5;2;3",exec_first="d0567",pj_type=qcg,venv=true
```

d0567 will be prioritized in job execution order.

## Multi-node execution and resource tuning

QCG-PilotJob can drive several nodes from a single SLURM allocation, and
FabSim3 wires this up already — no changes to the FabSim3 core are required.
You only choose how many nodes to ask for (via `cores`).

### How a SLURM allocation becomes QCG resources

1. Fabric computes the node count: `nodes = ceil(cores / corespernode)`
   (`calc_nodes()` in `fabsim/base/fab.py`).
2. The QCG header (`fabsim/deploy/templates/qcg-PJ-header`) submits
   `#SBATCH --nodes=$nodes --ntasks-per-node=$taskspernode --cpus-per-task=$cpuspertask`.
3. The manager is started as a `LocalManager` (`fabsim/deploy/templates/qcg-PJ-py`).
   With the default `resources='auto'`, QCG-PilotJob 0.14.x selects the SLURM
   allocation whenever `SLURM_NODELIST` and `SLURM_JOB_CPUS_PER_NODE` are set
   (`qcg/pilotjob/parseres.py`) — which is always true inside a batch job. It
   then sees the *whole* allocation (`total_nodes`, and
   `total_cores = nodes × taskspernode`).
4. For each allocated node, QCG fires a node agent with `srun -w <node> …`
   (`qcg/pilotjob/launcher/launcher.py`, `_fire_slurm_agent`). Every agent
   leaves a `QCG/nl-agent-<node>.log`, which is the quickest way to confirm
   that multiple nodes are actually being used.

!!! note
    The header also exports `QCG_PM_SRUN_CORES` and `QCG_PM_SRUN_NODES`. These
    are **not read** by QCG-PilotJob 0.14.x and can be ignored.

### Concurrency

```
concurrent_tasks = nodes × taskspernode ÷ cpuspertask
```

| nodes | taskspernode | cpuspertask | concurrent tasks |
|-------|--------------|-------------|------------------|
| 1     | 64           | 2           | 32               |
| 1     | 64           | 1           | 64               |
| 2     | 64           | 1           | 128              |
| 3     | 64           | 1           | 192              |

### Worked example: 3 nodes on ARCHER2

A 135-run ensemble finished in a **single wave** on 3 nodes:

```bash
fabsim archer2 <app>_ensemble:<config>,pj_type=qcg,venv=true,label=v3sweep \
       ,cores=384,cpuspertask=1,taskspernode=64,job_wall_time=0-12:00:00
```

- `cores / corespernode = 384 / 128 = 3` nodes.
- QCG logs confirmed one agent per node (`QCG/nl-agent-<node>.log`) and
  `Submitted 135 jobs`.

### Wall time

`job_wall_time` is a machine-level setting in `machines_user.yml`. The shipped
default for some machines is very short (minutes), so set it explicitly for real
workloads (override per run with `job_wall_time=H:M:S` or `D-HH:MM:SS`). For
reference, a single agent-based migration simulation in the
[FabFlee external-model case study](https://github.com/djgroen/FabFlee/blob/master/doc/RunningExternalModelOnARCHER2.md)
took ≈4.5 h.

### Choosing a layout

- **Single-threaded applications:** use `cpuspertask: 1` and set `taskspernode`
  to the largest number of processes a node can hold *safely* (bounded by
  memory), e.g. `64`.
- **Scale out, don't oversubscribe:** increase `cores` (i.e. add nodes) rather
  than multiplying processes per node beyond what memory allows.

## Troubleshooting

**Common Issues:**

1. **"QCG not found"** → Check `virtual_env_path` in `machines_user.yml`
2. **Resource allocation errors** → Verify `cpuspertask ≤ corespernode`
3. **Job submission fails** → Check machine-specific SLURM parameters
4. **Job killed after a few minutes** → `job_wall_time` is too small; set it in
   `machines_user.yml` or pass `job_wall_time=...`
5. **Only half as many tasks run at once as expected** → `cpuspertask` divides
   your concurrency; see [Concurrency](#concurrency)

**Debug Commands:**

```bash
# Check installation
fabsim <machine> direct_install_app:QCG-PilotJob,venv=True

# View job status
fabsim <machine> stat

# Check logs
fabsim <machine> fetch_results
```
